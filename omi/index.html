A fix inside Omi

Omi is an open-source AI wearable and desktop app. Its Mac app had a bug: chat, tasks and background synthesis all failed with the same database error. I traced it to one check, wrote a test that failed the same way, and fixed it. The fix was merged into main.

What broke

01

One database error took down three features in Omi's Mac app.

Omi's Mac app runs an agent in the background. It handles chat, runs tasks and does background synthesis. Along the way it saves sessions, runs and events to a small SQLite database on your Mac.

All three broke, and every time the error was the same: cannot start a transaction within a transaction.

The message was literal. The code asked SQLite to open a second transaction while one was already open. SQLite allows one at a time, so it refused, and the whole operation was undone.

Why it broke

02

A transaction inside a transaction, and a check that trusted the wrong answer.

SQLite
A small database that lives in one file. Omi's agent keeps its state there.
Transaction
A group of writes that all happen or none do. BEGIN starts one. COMMIT keeps the writes, ROLLBACK undoes them.
Nesting
Code that opened a transaction calls code that wants one too. Only the outermost call should send BEGIN.

Omi wraps its database writes in a helper called withTransaction. Big operations use it, and so do the smaller helpers they call, so one transaction often runs inside another. That's fine, as long as the inner call notices and just joins the transaction that's already open.

To notice, the old code asked the database: is a transaction open right now? That's the db.isTransaction flag. In the Node runtime bundled with the Mac app, the flag didn't reliably flip to true when a transaction was open. So every inner call thought it was first and sent its own BEGIN.

The fix

03

The commit title says it: track transaction depth in store instead of trusting db.isTransaction.

I gave the store its own counter, transactionDepth. Every withTransaction call adds one on the way in and takes one away on the way out.

If the counter is already above 0, the call is nested. It runs its work inside the open transaction and sends nothing to the database. Only the outermost call sends BEGIN, and only it sends COMMIT or ROLLBACK.

The count goes back down in finally blocks, so an error can't leave it stuck. And withTransaction never looks at the database's flag again.

How I proved it

04

A test that failed for the same reason the app did. Then the fix. Then the whole suite.

  1. FailTest first

    On the old logic, the inner call sends a second BEGIN and the fake database throws “cannot start a transaction within a transaction,” the same error as the app. The test never reaches its check.

  2. PassThen the fix

    With the counter in place, the inner call joins the outer one. The log reads BEGIN, COMMIT, and the test passes.

  3. 233/233Then everything

    The agent's whole test suite passes: 233 of 233.

The test is called “nests withTransaction safely when the runtime never reports isTransaction.” It runs one withTransaction inside another, the same shape as the app.

To make the bug show up on any machine, the test hands the store a fake database that acts like the bundled runtime. Its isTransaction is always false. Like real SQLite, it throws if a second BEGIN arrives while one is open. It also logs every BEGIN, COMMIT and ROLLBACK, so the test can check exactly what was sent.

The hook

A new databaseFactory option lets a test pass in its own database. Without it, the store uses Node's real DatabaseSync, same as before.

The fake

The flag never flips, and a second BEGIN throws the same message SQLite does. Every BEGIN, COMMIT and ROLLBACK goes into execLog.

The check

One transaction inside another. The inner result comes back, and the fake database saw exactly one BEGIN and one COMMIT.
